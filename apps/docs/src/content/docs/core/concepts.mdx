# Understanding Ecopages Core

Pages, layouts, and components are TypeScript modules. Core discovers routes, collects their assets, and either writes static HTML or serves them at request time. Integrations own how a file extension renders; processors own CSS, images, and other transforms.

This guide uses **Ecopages JSX** (`.tsx`). Other integrations share the same `eco.*` factories and `defineConfig()` shape.

## Integration System

Each Integration plugin declares:

1. File extensions it owns (for example `.tsx`)
2. A renderer and hydration contract
3. Optional `prepareBuildContributions()` for build-facing plugins

Register Integrations in `eco.config.ts`:

```typescript
import { defineConfig } from '@ecopages/core/config';
import { ecopagesJsxPlugin } from '@ecopages/ecopages-jsx';

export default defineConfig({
	rootDir: import.meta.dirname,
	integrations: [ecopagesJsxPlugin()],
});
```

Core then resolves semantic files such as `src/includes/html.*` and `src/pages/404.*` / `500.*` from those extensions. You do not name those files in config.

## CSS Processing

Plain CSS works without a processor: `import './page.css'` is discovered and emitted as a stylesheet.

Add `@ecopages/postcss-processor` when you need PostCSS, Tailwind, or **CSS imported as a string** in JavaScript (Lit `unsafeCSS`, runtime style injection).

```typescript
import path from 'node:path';
import { defineConfig } from '@ecopages/core/config';
import { ecopagesJsxPlugin } from '@ecopages/ecopages-jsx';
import { postcssProcessorPlugin } from '@ecopages/postcss-processor';
import { tailwindV4Preset } from '@ecopages/postcss-processor/presets/tailwind-v4';

const appRoot = import.meta.dirname;

export default defineConfig({
	rootDir: appRoot,
	processors: [
		postcssProcessorPlugin(
			tailwindV4Preset({
				referencePath: path.resolve(appRoot, 'src/styles/tailwind.css'),
			}),
		),
	],
	integrations: [ecopagesJsxPlugin()],
});
```

See [PostCSS Processor](/docs/ecosystem/postcss-processor) for presets and `postcss.config.js`.

## Script and CSS loading

Ecopages injects scripts and CSS by walking declared Component Dependencies.

### Discovered and explicit Dependencies

In modules that declare `eco.component()`, `eco.layout()`, `eco.html()`, or `eco.page()`, and in MDX compiled through `@ecopages/mdx/core`:

- Direct local Eco Component imports and relative or aliased side-effect CSS imports are discovered automatically.
- Browser scripts stay explicit in `dependencies.scripts`. Ecopages does **not** detect script files by name (`*.script.ts` is a convention, not a requirement).
- Explicit `dependencies.stylesheets` entries override discovered references to the same resolved file (for example `media="print"`). Discovered CSS is not copied into that array.

```tsx
import { BaseLayout } from '@/layouts/base-layout';
import { eco } from '@ecopages/core';
import './home-page.css';

export default eco.page({
	layout: BaseLayout,
	dependencies: {
		scripts: ['./home-page.script.ts'],
	},
	render: () => (
		<div class="main-content">
			<h1>Welcome to Ecopages</h1>
		</div>
	),
});
```

### Lazy scripts

Defer browser scripts with per-entry `dependencies.scripts[].lazy`:

- `on:idle`: when the browser is idle
- `on:visible`: when the element enters the viewport
- `on:interaction`: on user interaction (for example mouseover, click, focus)

```tsx
import { eco } from '@ecopages/core';

export const HeavyPanel = eco.component({
	dependencies: {
		scripts: [{ src: './heavy-panel.script.ts', lazy: { 'on:visible': true } }],
	},
	render: () => <div>Heavy Content</div>,
});
```

For Radiant hosts and Lit elements that must SSR, add `ssr: true` on the same entry. See [Components](/docs/core/components).

## Import CSS as a string

Side-effect imports (`import './file.css'`) become page stylesheets. To get the **processed CSS text** in JavaScript, use a default import. That path requires `@ecopages/postcss-processor` in `eco.config.ts`.

```typescript
import styles from './lit-counter.css';
```

`styles` is a string. Typical use is Lit `unsafeCSS(styles)` inside a custom element script:

```typescript
import { LitElement, unsafeCSS } from 'lit';
import { customElement } from 'lit/decorators.js';
import styles from './lit-counter.css';

@customElement('lit-counter')
export class LitCounter extends LitElement {
	static override styles = [unsafeCSS(styles)];
}
```

Without the PostCSS processor, this import does not resolve to a CSS string. Types for `*.css` modules come from `import '@ecopages/core/declarations'`.

See [PostCSS Processor: Using CSS Imports](/docs/ecosystem/postcss-processor#using-css-imports).

## Import MDX as a component

The [MDX Integration](/docs/integrations/mdx) (or `ecopagesJsxPlugin({ mdx: { enabled: true } })`) lets you import MDX files as components:

```tsx
import ShowcaseMdx from '@/components/showcase.mdx';
import { eco } from '@ecopages/core';

export default eco.page({
	render: () => <ShowcaseMdx />,
});
```

## Robots.txt and sitemap

Ecopages writes `robots.txt` on every static export from `robotsTxt` / `setRobotsTxt()` preferences.

Optional `sitemap.xml` generation is separate and disabled by default. Enable it with `sitemap: { enabled: true }`. See [Sitemap](/docs/core/sitemap).

## Project structure

```
my-project/
├── src/
│   ├── pages/
│   ├── layouts/
│   ├── components/
│   ├── includes/
│   ├── styles/
│   └── public/
├── app.ts
├── eco.config.ts
└── package.json
```

| Path | Role |
| --- | --- |
| `src/pages/` | Filesystem routes (**default**, required for file-based apps) |
| `src/includes/` | `html`, `head`, `seo` templates (**default**) |
| `src/layouts/` | Route layouts (recommended) |
| `src/components/` | Reusable UI (recommended) |
| `src/public/` | Copied to `dist` (`publicDir` is relative to `src`) |
| `eco.config.ts` | **Required**: author with `defineConfig()` |
| `app.ts` | `createApp()` entry |

Override directories in [Configuration](/docs/getting-started/configuration). Semantic filenames (`html.*`, `404.*`, `500.*`) are not configurable.

## Runtime origin and API requests

When fetching data in `staticPaths` or `staticProps`, **call your data functions directly**. Do not HTTP-fetch your own app during static generation.

```tsx
import { eco } from '@ecopages/core';
import { getAllBlogPosts, getBlogPost } from '@/data/blog';

export default eco.page({
	staticPaths: async () => {
		const posts = getAllBlogPosts();
		return {
			paths: posts.map((post) => ({
				params: { slug: post.slug },
			})),
		};
	},
	staticProps: async ({ pathname }) => {
		const post = getBlogPost(pathname.params.slug);
		if (!post) {
			throw new Error(`Post not found: ${pathname.params.slug}`);
		}
		return { props: { post } };
	},
	render: ({ post }) => <article>{post.title}</article>,
});
```

## Runtime support

`createApp()` from `@ecopages/core/create-app` selects the adapter automatically: Bun when `globalThis.Bun` exists, otherwise Node. Pass `adapter: 'node'` or `adapter: 'bun'` only to force one.

Install dependencies with any package manager. The same `app.ts` and `ecopages` CLI scripts run on both runtimes. See [Build and Host](/docs/core/build-and-host) and [Deployment](/docs/reference/deployment).

## Server and API handlers

```typescript
import { createApp } from '@ecopages/core/create-app';

const app = await createApp();

app.get('/api/hello', async (ctx) => {
	return ctx.response.json({ message: 'Hello world!' });
});

await app.start();
```

Details: [Server API](/docs/server/server-api).
