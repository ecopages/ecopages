# Understanding Ecopages Core

Before diving into the specifics of writing code for Ecopages, it's important to understand how the core of Ecopages works. This knowledge will help you make better decisions when structuring your project and writing your code.

## Integration System

Ecopages uses a flexible integration system to extend its functionality. Each integration plugin can provide:

1. Template extensions
2. Custom loaders
3. `plugins(app)` for build-facing declarations

For example, the KitaJS integration might set up template extensions like this:

```typescript
import { defineConfig } from '@ecopages/core/config';
import { kitajsPlugin } from '@ecopages/kitajs';

// html.kita.tsx, 404.kita.tsx, and 500.kita.tsx are discovered automatically
export default defineConfig({ integrations: [kitajsPlugin()] });
```

Those extensions are then used to resolve semantic files such as `html.*`, `404.*`, and `500.*`.

## CSS Processing

By default, Ecopages uses plain css for styling.
The starter templates use the [Lightning CSS Processor](/docs/ecosystem/lightningcss-processor), which runs Tailwind v4 through a preset and supports CSS Modules. The [PostCSS Processor](/docs/ecosystem/postcss-processor) stays available for PostCSS plugins and Tailwind v3.
You can customize this in your `eco.config.ts` file:

```typescript
import path from 'node:path';
import { defineConfig } from '@ecopages/core/config';
import { ecopagesJsxPlugin } from '@ecopages/ecopages-jsx';
import { lightningCssProcessorPlugin } from '@ecopages/lightningcss-processor';
import { tailwindV4Preset } from '@ecopages/lightningcss-processor/presets/tailwind-v4';

const appRoot = process.cwd();

export default defineConfig({
	rootDir: appRoot,
	processors: [
		lightningCssProcessorPlugin({
			...tailwindV4Preset({
				referencePath: path.resolve(appRoot, 'src/styles/tailwind.css'),
			}),
			targets: ['chrome >= 111', 'safari >= 16.4', 'firefox >= 128'],
		}),
	],
	integrations: [ecopagesJsxPlugin()],
});
```

## Script and CSS Loading

Ecopages injects scripts and CSS by walking declared Component Dependencies.

### Discovered and explicit Dependencies

In modules that declare `eco.component()`, `eco.layout()`, `eco.html()`, or `eco.page()`, and in MDX compiled through `@ecopages/mdx/core`:

- Direct local Eco Component imports and relative or aliased side-effect CSS imports are discovered automatically.
- A side-effect import of a package stylesheet, such as `import 'react-day-picker/style.css'`, is discovered the same way. A specifier ending in `.css` resolves through the package's `exports`, preferring the `style` condition; any other specifier, such as `import 'swiper/css'`, counts only when the package resolves it to a `.css` file. Ecopages links the stylesheet once and copies the fonts and images its relative `url()` references into the build. Your CSS Processor (PostCSS, Tailwind) does not run on it, so a package must ship built CSS: importing a package file your Processor handles, such as `some-lib/theme.scss`, fails the build. The build fails when such a `url()` or a relative `@import` names a missing file. Only fonts, images and media are copied, never a dotfile; any other file a `url()` names is left as written with a warning.
- Plain CSS needs no Processor. Ecopages inlines the relative `@import`s of a stylesheet in the build (`@import './partials/buttons.css';`, with `layer()`, `supports()` and media conditions), copies the fonts, images and media files its relative `url()` references name, and rewrites the references to the copies. A missing partial or file logs a warning that names the importing file and leaves the reference as written; in development, creating the file fixes it with no restart.
- Plain function components are followed too: their side-effect CSS reaches the page through the nearest declared component, layout or page that imports them, and editing their imports in development refreshes the page's stylesheets.
- Cascade order: explicit `dependencies.stylesheets` come first, then each declaration's own imported CSS, each before the CSS of the plain components it imports. A stylesheet that plain components reach from several declarations on the page takes the position of its last occurrence, after the CSS of every declaration importing it.
- In development and in `ecopages build`, the build fails, naming the file and the import, for a plain module's side-effect CSS import inside the app that no declaration reaches, and for a CSS Module import when no stylesheet Processor scopes CSS Modules (it names the importer, the specifier and `@ecopages/lightningcss-processor`). Modules outside the app root, such as linked workspace packages, are treated as packages and not checked.
- `import styles from './card.module.css'` gives the component a map of its local class names to scoped ones, and the scoped CSS reaches the Page like side-effect CSS, from the declaration that imports the module. It needs a Processor that scopes CSS Modules, such as [Lightning CSS](/docs/ecosystem/lightningcss-processor); a CSS Module imported from a package works the same way. A browser script that imports a CSS Module gets the same class names, but the CSS reaches the Page only when the component that uses the script also imports the module or lists it in `dependencies.stylesheets`.
- Wrap a component in `eco.component()` only when it needs browser scripts, `modules`, stylesheet attributes, an `integration` override, or rendering by another Integration. A layout is a plain function typed with `LayoutProps` unless it needs one of those, then `eco.layout()`; the document shell uses `eco.html()`.
- Browser scripts stay explicit in `dependencies.scripts`. Ecopages does **not** detect script files by name pattern.
- Explicit `dependencies.stylesheets` entries override discovered references to the same resolved file (for example `media="print"`). Discovered CSS is not copied into that array.

```tsx
import { BaseLayout } from '@/layouts/base-layout';
import { eco } from '@ecopages/core';
import './home-page.css';

const HomePage = eco.page({
	layout: BaseLayout,
	dependencies: {
		scripts: ['./home-page.script.ts'],
	},
	render: () => (
		<div class="main-content">
			<h1>Welcome to Ecopages</h1>
		</div>
	),
});
```

### Lazy Dependencies

You can also defer loading of scripts until they are needed using per-entry `dependencies.scripts[].lazy` options. This is useful for improving initial page load performance.

The supported triggers are:

- `on:idle`: Loads when the browser is idle.
- `on:visible`: Loads when the element enters the viewport.
- `on:interaction`: Loads when the user interacts with the element (e.g. mouseover, click, focus).

```typescript
const MyComponent = eco.component({
	dependencies: {
		scripts: [{ src: './heavy-script.ts', lazy: { 'on:visible': true } }], // or provide a specific selector string
	},
	render: () => <div>Heavy Content</div>,
});
```

## Robots.txt and sitemap

Ecopages writes `robots.txt` on every static export from the `robotsTxt` preferences in `eco.config.ts`.

Optional `sitemap.xml` generation is separate and disabled by default. Enable it with `sitemap: { enabled: true }` — see [Sitemap](/docs/core/sitemap) for eligibility, `exclude`, `extraUrls`, and page-level `metadata.robots.index`.

## Import CSS as String in JS Files

Ecopages provides a way to load CSS directly into your JavaScript files as strings through Ecopages build plugins. This feature is enabled when you register a stylesheet Processor, such as `@ecopages/lightningcss-processor` or `@ecopages/postcss-processor`, in your `eco.config.ts`.

## Import MDX as a Component

Ecopages allows you to import MDX files as components. This is useful for creating reusable content and components that can be used across your site.

This capability is provided by the [MDX Integration](/docs/integrations/mdx), which automatically handles MDX transformations.

```typescript
import Component from '@/components/mdx-component';

const MyPage = () => Component();
```

## Project Structure

Ecopages expects a specific project structure:

```
my-project/
├── src/
│ ├── pages/
│ ├── layouts/
│ ├── components/
│ ├── includes/
│ └── public/
├── eco.config.ts
└── package.json

```

- `src/components/`: Stores reusable components (Recommended)
- `src/pages/`: Contains your page files (e.g., `.tsx`, `.mdx`, `.kita.tsx`, `.lit.tsx`, or plain `.html` [HTML Pages](/docs/core/pages#html-pages)) (**Default**)
- `src/layouts/`: Holds layout components (Recommended)
- `src/includes/`: Contains include templates (e.g., `head.tsx`, `html.tsx`, or integration-specific suffixes) (**Default**)
- `src/public/`: Static assets copied to the build directory as written (Default)
- `eco.config.ts`: Ecopages configuration file (**Mandatory**)

This structure helps Ecopages efficiently process and build your site. While Ecopages provides these sensible defaults, every directory path is fully customizable via your `eco.config.ts`.

## Runtime Origin and API Requests

When fetching data in `paths` or `props`, Ecopages provides different approaches. **For most cases, calling your data functions directly is recommended** for better performance and reliability.

### Direct Function Calls (Recommended)

For the best performance during static generation, call your data layer functions directly:

```tsx
import { eco } from '@ecopages/core';
import { getAllBlogPosts, getBlogPost } from '@/data/blog';

export default eco.page({
	paths: async () => {
		const posts = getAllBlogPosts();

		return posts.map((post) => ({
			params: { slug: post.slug },
		}));
	},

	props: async ({ pathname }) => {
		const slug = pathname.params.slug;
		const post = getBlogPost(slug);

		if (!post) {
			throw new Error(`Post not found: ${slug}`);
		}

		return { post };
	},

	render: ({ post }) => <article>{post.title}</article>,
});
```

## Runtime Support

Ecopages runs on Node or Bun through Node APIs. The CLI picks the runtime that launched it.

This means you'll need to:

- Launch the app with Node or with Bun
- Install dependencies with your preferred package manager (for this repo, `pnpm` is used)
- Ensure that runtime can execute your app entrypoint and scripts

## Server and API Handlers

Ecopages provides a simple and intuitive way to create API endpoints and handle server-side logic. You can find more details in the [Server API](/docs/server/server-api) documentation. A handler can also be an endpoint file (`*.api.ts`, or `.api.tsx`, `.api.js`, `.api.jsx`) under `src/pages`; see [Endpoint Files](/docs/server/endpoint-files).

```typescript
import { createApp } from '@ecopages/core/create-app';

const app = await createApp();

app.get('/api/hello', async () => {
	return new Response(JSON.stringify({ message: 'Hello world!' }));
});

await app.start();
```

## Additional Features

- **Hot Reload**: Ecopages supports hot reloading during development, making the development process more efficient.
- **Static Site Generation**: Ecopages generates static HTML files, improving performance and reducing server load.
- **TypeScript Support**: Ecopages is built with TypeScript and provides excellent TypeScript support out of the box.
