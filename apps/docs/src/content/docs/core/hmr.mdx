# Hot Module Replacement (HMR)

During `ecopages dev`, Ecopages watches the project and updates the browser without a full rebuild. Core classifies the change; Integrations and processors decide whether that is a CSS swap, a module update, React Fast Refresh, or a reload.

## How it works

1. **Project watcher** observes file changes.
2. **Invalidation service** classifies the change (config, dotenv, page, script, CSS, other).
3. **HMR manager** selects a strategy (Integration, processor, script, or fallback).
4. **Client bridge** (WebSocket on `/_hmr`) applies the event in the browser.

Client events:

| Event | Browser behavior |
| --- | --- |
| `css-update` | Refresh matching stylesheet `<link>` hrefs: no full reload |
| `update` | Cache-bust and re-import the changed module URL |
| `layout-update` | Soft current-page reload with layout cache cleared |
| `reload` | Full `location.reload()` |
| `error` | Log the failure; a reload may follow |

## What actually hot-updates

- **CSS**: the [PostCSS processor](/docs/ecosystem/postcss-processor) broadcasts `css-update` for stylesheets it owns, including `@import` graphs. Without that processor, a CSS change typically falls through to a full reload.
- **Declared browser scripts**: any file listed in `dependencies.scripts` is a registered entrypoint. `JsHmrStrategy` rebuilds watched entrypoints and either hot-accepts the module or reloads. The filename does **not** have to be `*.script.ts`; that suffix is a convention.
- **React Fast Refresh**: the React Integration registers its own strategy so component updates can keep state.
- **Pages, layouts, includes**: server-rendered templates usually reload or emit `layout-update` so SSR HTML stays consistent.
- **`eco.config.ts` and `.env`**: these restart the process; they are not in-process HMR.

## Client scripts

Register the file on the component, layout, or page that owns it:

```tsx
dependencies: {
	scripts: ['./widget.ts'],
}
```

or with SSR preload / lazy delivery:

```tsx
dependencies: {
	scripts: [{ src: './counter.script.ts', ssr: true, lazy: { 'on:visible': true } }],
}
```

HMR keys off that registration (and the dependency graph of those entrypoints), not off a glob of `*.script.ts` files. Unregistered TypeScript in `src/` that no entrypoint imports will not get a targeted script update.

## Customizing HMR

If you are building a [Custom Integration](/docs/plugins/custom-integration), define a strategy by extending `HmrStrategy`.

```typescript
import { HmrStrategy, HmrStrategyType, type HmrAction } from '@ecopages/core/hmr/hmr-strategy';

class MyCustomStrategy extends HmrStrategy {
	readonly type = HmrStrategyType.INTEGRATION;

	matches(filePath: string) {
		return filePath.endsWith('.myext');
	}

	async process(filePath: string): Promise<HmrAction> {
		return {
			type: 'broadcast',
			events: [{ type: 'update', path: filePath, timestamp: Date.now() }],
		};
	}
}
```

## Troubleshooting

- **WebSocket**: `/_hmr` uses the same host and port as the dev server. Proxies must forward WebSockets.
- **Console**: `[ecopages] HMR` logs report a failed hot-update that fell back to reload.
- **Nothing happens**: confirm the file is imported (CSS) or listed in `dependencies.scripts` (browser JS). Config and env edits require a process restart.
