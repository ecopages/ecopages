# Request Locals

Request locals are values attached to one HTTP request. Middleware provides them with `createMiddleware`, and request-time Pages, layouts, and API handlers can read them. Ecopages does not persist them between requests.

## Provide locals in middleware

`createMiddleware` makes a middleware that provides typed locals. The stage continues with `next(locals)`, and what it passes becomes `ctx.locals` for every later stage and for the handler or Page. The type is read from the `next` call, with no declaration:

```typescript
import { createMiddleware } from '@ecopages/core';

export const authMiddleware = createMiddleware(async (ctx, next) => {
	const session = await authService.validateRequest(ctx.request);
	if (!session) {
		return Response.redirect(new URL('/login', ctx.request.url));
	}
	return next({ session, requestId: crypto.randomUUID() });
});
```

A guard answers by returning a `Response` without calling `next`. Page middleware runs on every request, so the Page must use `cache: 'dynamic'`. The Page reads the provided values from `locals` in `render`, typed from its `middleware` list:

```tsx
import { eco } from '@ecopages/core';
import { authMiddleware } from '@/middleware/auth';

export default eco.page({
	cache: 'dynamic',
	middleware: [authMiddleware],
	render: ({ locals }) => <Dashboard user={locals.session.user} />,
});
```

API handlers read the same values from `ctx.locals`. See [Define Handlers](/docs/server/define-handlers#middleware).

## Compose stages

`composeMiddleware` joins middleware and inline stages in order. A later stage reads what the earlier ones provided from `ctx.locals`, typed, and the result is itself a middleware you can list or compose again:

```typescript
import { composeMiddleware } from '@ecopages/core';

export const adminMiddleware = composeMiddleware(authMiddleware, (ctx, next) => {
	if (ctx.locals.session.user.role !== 'admin') {
		return new Response('Forbidden', { status: 403 });
	}
	return next({ isAdmin: true });
});
```

It types up to four stages; nest compositions beyond that.

## Rules

- A stage may call `next` only once. A second call throws.
- A stage may call `next` only before it returns. A call from a timer or callback after the stage returned or threw throws, and the rest of the chain does not run.
- A stage that called `next` must return the response `next` resolved with, awaited or not. It may edit that response's headers first. Returning a different response throws, even when the stage did not await `next`. When the rest of the chain throws, the stage may catch the error and return its own response.
- A later entry in a `middleware` list overrides an earlier one that provides the same key, in the types and at runtime.
- The same stage twice in one list or composition is rejected when the route or Page is defined. Declare a shared guard once, in the composition that owns it.
- A list typed as a plain array, such as `Middleware[]`, provides no reliable locals. Write the list inline or as a constant tuple.
- An entry typed `AnyEcoMiddleware` may provide anything, so no key before it in the list is typed afterwards; a later entry types its own keys again. A middleware cannot be widened to `EcoMiddleware` or built as a plain object: only `createMiddleware` and `composeMiddleware` make one.
- `next()` provides nothing and `next(locals)` provides `locals`. A value that may be `undefined` does not type-check: call `next()` on that path instead.
- A plain `(ctx, next) => ...` function still works in a list and provides nothing. In the `options` of `app.get()` and its siblings, which come after the handler, declare it as a constant: written inline, it leaves the handler with no locals.
- List `middleware` before `handler`, so TypeScript infers the list first.

## Declare locals for layouts

Layouts read locals through the global `RequestLocals` interface, not a `middleware` list. Augment it in a declaration file such as `src/modules.d.ts` for the values a Layout reads:

```typescript
import '@ecopages/core';

declare module '@ecopages/core' {
	interface RequestLocals {
		session?: {
			user: { id: string; email: string; role: 'admin' | 'user' };
		} | null;
		requestId?: string;
	}
}
```

Keep the fields optional, since middleware may not set them for every route.

A Page with a typed `middleware` list gets its `locals` from the list. `requires` still narrows a `RequestLocals` field to non-null for a Page without a typed list, and on any Page it decides which locals reach the browser:

```tsx
export default eco.page({
	cache: 'dynamic',
	requires: ['session'],
	render: ({ locals }) => <Dashboard user={locals.session.user} />,
});
```

`requires` is a type-only contract. Ecopages does not check at runtime that middleware populated those locals, so do not use it as an authentication check. For React Pages, `requires` also decides which locals are sent to the browser. See [TypeScript Types](/docs/reference/typescript) for the public type definitions.

API handlers also receive `ctx.require('session', onMissing)`, which checks at runtime that a local is present and non-null, then returns its narrowed value. If it is missing, the helper terminates the request with the `Response` returned by `onMissing`.

Without a typed list or `requires`, check optional locals before using them:

```tsx
export default eco.page({
	cache: 'dynamic',
	render: ({ locals }) => {
		if (!locals?.session) {
			return <GuestView />;
		}
		return <UserView user={locals.session.user} />;
	},
});
```

## Layouts

A Layout does not receive `locals`. It receives request data only through the `props` factory of its layout entry on the Page. The factory runs on the server with `locals`, `params` and `query`, the Layout renders with what it returns, and the same result is sent to the browser for hydration. Return only what the browser may see: narrow the session to the user instead of passing a token.

```tsx
import { eco } from '@ecopages/core';
import { BaseLayout } from '@/layouts/base-layout';

export default eco.page({
	layout: {
		component: BaseLayout,
		props: ({ locals }) => ({ user: locals?.session?.user }),
	},
	cache: 'dynamic',
	render: () => <h1>Dashboard</h1>,
});
```

The Layout declares `user` as an optional prop. On a static or revalidating Page there are no `locals`: the factory still runs with `locals` undefined, so read it with `locals?.`, and the Layout renders without `user`, so keep a fallback for it.

## Cache behavior

Request locals are available only during request-time rendering for Pages with `cache: 'dynamic'`. A static Page or a Page with a revalidation cache cannot use request locals. Reading locals while such a Page renders throws `LocalsAccessError`. Page middleware also requires `cache: 'dynamic'`.

| Page cache | Request locals |
| --- | --- |
| `dynamic` | Available during each request |
| `static` | Unavailable; access throws `LocalsAccessError` |
| `{ revalidate: seconds }` | Unavailable; access throws `LocalsAccessError` |

Semantic error-page renders bypass the normal Page middleware pipeline and receive an empty `pageLocals` object. Do not rely on Page middleware to provide locals there. See [Routing](/docs/core/routing) for error-page behavior.
