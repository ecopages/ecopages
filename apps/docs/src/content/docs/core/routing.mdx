# Routing

Ecopages uses file-based routing for pages and endpoint files, and Explicit Routes in `app.ts`.

## File-Based Routing

Every file in your `src/pages` directory corresponds to a route. The path relative to `src/pages` determines the URL.

### Supported File Extensions

Extensions depend on your active integrations:

- `.tsx` — [Ecopages JSX](/docs/integrations/ecopages-jsx) (default in Installation)
- `.kita.tsx` — [KitaJS](/docs/integrations/kitajs)
- `.tsx` with [React](/docs/integrations/react) when React owns the route
- `.lit.tsx` — [Lit](/docs/integrations/lit)
- `.mdx` — [MDX](/docs/integrations/mdx)
- `.html` — [HTML Pages](/docs/core/pages#html-pages), no integration needed

Each route must come from exactly one file, whatever its parameter names. For example, `about.html` next to `about.tsx`, `about.tsx` next to `about/index.tsx`, or `blog/[slug].tsx` next to `blog/[id].tsx`, is an error. HTML Pages cannot use dynamic segments such as `[slug].html`.

### Index Routes

- `src/pages/index.tsx` → `/`
- `src/pages/blog/index.tsx` → `/blog`

### Nested Routes

- `src/pages/about/team.tsx` → `/about/team`
- `src/pages/v1.2.html` → `/v1.2`

A dot in the last segment is part of the route. The server treats a path as a file only when it ends in a known static extension, such as `.js`, `.css`, `.png`, or `.html`.

## Dynamic Routes

Use bracket syntax: `[param]`.

- `src/pages/blog/[slug].tsx` → `/blog/[slug]`
- `src/pages/users/[id]/profile.tsx` → `/users/[id]/profile`

Access params via `staticPaths` and `staticProps` on `eco.page` views, or at request time with `cache: 'dynamic'`.

### Catch-all Routes

- `src/pages/docs/[...slug].tsx` → `/docs/a`, `/docs/a/b`, `/docs/v1.2`

A catch-all also matches a path with a dot, such as `/docs/v1.2`, unless that path ends in a known static extension. A path that does end in one of those extensions is a file, so a catch-all does not render it.

For a Page request to `/docs/a/b`, `params.slug` is `['a', 'b']`. A single `[slug]` segment stays a string. Repeated query keys are arrays, so `?tag=docs&tag=api` becomes `query.tag === ['docs', 'api']` on page props and route info.

## Endpoint Files

A file under `src/pages` whose name ends in `.api.ts`, `.api.tsx`, `.api.js` or `.api.jsx` is an endpoint file, not a page. Its URL follows the same rules as a page: drop the whole `.api.*` ending, drop `index`, keep the brackets. `api/` has no special meaning; it is just a folder.

```text
src/pages/health.api.ts                ->  /health
src/pages/api/users/index.api.ts       ->  /api/users
src/pages/api/users/[id].api.ts        ->  /api/users/[id]
src/pages/api/docs/[...slug].api.ts    ->  /api/docs/[...slug]
src/pages/blog/[slug]/comments.api.js  ->  /blog/[slug]/comments
src/pages/users.api.tsx                ->  /users
```

The `.api.*` endings are reserved: an Integration cannot register one as a page extension, and the config fails with an error naming the Integration that does. Registering `.tsx` is fine; `users.api.tsx` is still an endpoint file, not a `.tsx` page.

Endpoint files use brackets (`[id]`, `[...slug]`); `:id` is for `app.ts` routes. A request to `/api/users/5` gives `params.id === '5'`, and a catch-all param is an array.

The file exports one handler per HTTP method, named exactly `GET`, `POST`, `PUT`, `DELETE`, `PATCH`, `OPTIONS`, `HEAD` or `QUERY`, built with the matching method helper and no `path`. Other exports are ignored.

```typescript
// src/pages/health.api.ts
import { defineGet } from '@ecopages/core';

export const GET = defineGet({
	handler: async ({ response }) => response.json({ ok: true }),
});
```

- The app still needs its `app.ts` entry (`createApp()` and `app.start()`); it need not register any route.
- A request whose method the file does not export answers `405` with an `Allow` header listing the methods it does export. `HEAD` and `OPTIONS` are not added for you. A cross-origin request sends an `OPTIONS` preflight; export `OPTIONS` to answer it, otherwise it gets `405`.
- An unknown `[slug]` still reaches the handler; return `404` from it.
- A file with no method export, or a method export that is not a handler, is built for another method, or sets `path`, fails `ecopages build` with an error naming the file: the build imports each endpoint file to check its exports, as it imports Pages, so the file's top-level code runs at build time. In `ecopages dev` the error shows on the file's first request: the request answers `500`, or goes to `app.onError`; the logged error, or the one passed to `app.onError`, names the file.
- Schemas, middleware and `app.onError` work as they do for `app.ts` routes.
- Two files on the same route fail at startup, whatever the parameter names: `users.tsx` beside `users.api.ts`, `users.api.ts` beside `users.api.js`, or `blog/[slug].tsx` beside `blog/[id].api.ts`.
- The server skips file routes for a URL that ends in a known static file extension (`.json`, `.xml`, `.csv`, `.txt`, ...), so no endpoint file answers it: `files/[name].api.ts` does not answer `/files/report.csv`, and an endpoint file named like `feed.xml.api.ts` fails discovery. Register such a URL in `app.ts`, which is matched first.
- In `ecopages dev`, saving an endpoint file reloads it without a restart.
- Like `app.ts` routes, endpoint files need a running server: they are never rendered to static HTML, never appear in the sitemap, and `ecopages preview` does not serve them.

See [Define Handlers](/docs/server/define-handlers#endpoint-files) for schemas and middleware in endpoint files.

## Routes in `app.ts`

`app.ts` routes are defined on your app instance:

```typescript
import { createApp } from '@ecopages/core/create-app';

const app = await createApp();

app.get('/api/users/:id', async ({ params, response }) => {
	return response.json({ userId: params.id });
});

app.get('/api/files/[...path]', async ({ params, response }) => {
	return response.json({ path: params.path });
});

await app.start();
```

Use `app.add(handler)` for handlers created with `defineApiHandler`. See [Define Handlers](/docs/server/define-handlers).

An `app.ts` catch-all keeps each decoded path segment in an array. A request to `/api/files/docs/a` gives `params.path === ['docs', 'a']`. A named segment such as `:id` remains a string. Repeated query keys also stay as arrays on `ctx.query`; schemas receive the same parsed values before validation.

### Route Priority

1. **`app.ts` routes**, then `app.static()` routes
2. **File-based pages and endpoint files** in `src/pages`, unless the path ends in a known static extension
3. **Static files** from `public` and the build output

An `app.ts` route registered on an endpoint file's URL keeps the methods it registers, and the file answers the rest. `:slug` and `[slug]` name the same URL.

```typescript
// app.ts
app.get('/blog/:slug/comments', handler); // GET goes here
// POST /blog/:slug/comments still goes to src/pages/blog/[slug]/comments.api.ts
```

Startup logs a warning naming the `app.ts` route and the endpoint file.

`app.ts` routes are matched before any file, so `app.get('/api/users/:id')` also answers `GET /api/users/me` when `api/users/me.api.ts` exists. Startup warns only when both name the same route.

## Route Configuration

Set the canonical base URL in `eco.config.ts`:

```typescript
import { defineConfig } from '@ecopages/core/config';
import { ecopagesJsxPlugin } from '@ecopages/ecopages-jsx';

export default defineConfig({
	rootDir: import.meta.dirname,
	baseUrl: 'https://example.com',
	integrations: [ecopagesJsxPlugin()],
});
```

### 404 Page

Create `404.tsx` (or the extension of your integration, or `404.html`) under `src/pages`. Unmatched page requests render this template with status 404.

### 500 Page

Create `500.tsx` (or the extension of your integration, or `500.html`) under `src/pages`. When a **page** render fails in the file-route pipeline, Ecopages renders this template with status 500.

### Precedence

1. **`src/pages/404.*` / `500.*`** — highest priority when the file exists.
2. **`app.notFound()` / `app.serverError()`** — lazy view loaders for explicit-route apps without a `pages/` error file.
3. **Built-in HTML defaults** — basic pages shipped by the framework when neither of the above is configured. They include inline CSS and `eco-error-page*` class hooks; they do not load your app stylesheets.

Custom error pages (filesystem or `app.notFound()` / `app.serverError()`) use your layout and assets. Typical class names are `error404`, `error500`, and `error500__stack` with optional `dependencies.stylesheets`.

### 500 Page behavior

Important:

- Applies to page rendering (matched routes and a failing custom 404). API handlers keep their own `errorHandler` / JSON response path.
- If the custom `500.*` template or app loader is missing or throws, the response falls back to the built-in HTML error page. The custom page is never retried.
- In **development**, the thrown error is passed as page props (`message`, `stack`) so the custom 500 page can show the real failure. In **production**, those props are omitted so stacks are not serialized into HTML. The original error is always logged server-side.
- Like `404.*`, the file is also a normal route at `/500`, so you can open it directly to preview the design (that direct visit is a 200 and has no error props unless you trigger a render failure).
- Semantic error templates render outside the normal page-request middleware pipeline. They receive a safe empty `pageLocals` object instead of request-scoped `locals`. Do not use `cache: 'dynamic'`, `middleware`, or `requires` on `404.*` / `500.*` templates.

```tsx
import { eco, type ErrorPageTemplateProps } from '@ecopages/core';

export default eco.page<ErrorPageTemplateProps>({
	render: ({ message, stack }) => (
		<div>
			<h1>Something went wrong</h1>
			{message ? <p>{message}</p> : null}
			{stack ? <pre>{stack}</pre> : null}
		</div>
	),
});
```

## Summary

| Type | Definition | Usage |
| :--- | :--- | :--- |
| **Static pages** | `src/pages/*.{ext}` | Marketing, docs, blogs |
| **Dynamic pages** | `src/pages/[slug].{ext}` | Posts, profiles |
| **Error pages** | `src/pages/404.*`, `src/pages/500.*` | Not-found and server-error HTML |
| **Endpoint files** | `src/pages/**/*.api.{ts,tsx,js,jsx}` | Data, forms, webhooks |
| **`app.ts` routes** | `app.get('/api/...')` | Data, forms |
