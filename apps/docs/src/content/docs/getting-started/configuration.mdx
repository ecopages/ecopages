# Configuration

Ecopages can be customized to fit your project's needs through a configuration file. Create a file named `eco.config.ts` in your project's root directory to get started.

Here's a basic example of an Ecopages configuration:

```typescript
import { defineConfig } from '@ecopages/core/config';
import { ecopagesJsxPlugin } from '@ecopages/ecopages-jsx';

export default defineConfig({
	integrations: [ecopagesJsxPlugin()],
	defaultMetadata: {
		title: 'Your Site Title',
		description: 'Your site description',
		image: 'https://your-domain.com/og-image.png',
	},
});
```

`createApp()` loads and finalizes this file automatically. Override the path with `createApp({ configFile })`, `ECOPAGES_CONFIG_FILE`, or `ecopages dev --config <file>`.

When one process needs to create more than one app from the same config module, export a factory so each app gets fresh plugin instances:

```typescript
export default defineConfig(() => ({
	integrations: [ecopagesJsxPlugin()],
}));
```

An object config containing integrations, processors, or loaders can create one app. Loading it again for another app throws because those plugin instances carry app state.

In development, adding, changing, or removing `eco.config.ts` or a supported project `.env` file restarts the dev server so integrations, directories, and environment values reload. Supported files are `.env`, `.env.local`, `.env.[NODE_ENV]`, and `.env.[NODE_ENV].local`. If the restarted dev server exits with an error, for example because of an invalid `eco.config.ts`, `ecopages dev` waits for the next change in the project or a linked workspace package and starts again. Page and component files still hot-reload without a full restart.

## Configuration API

<ApiField name="rootDir" defaultValue="process.cwd()" type="string">
	The root directory of your project, used to resolve paths to your project files.
</ApiField>

<ApiField name="baseUrl" defaultValue="http://localhost:3000" type="string">
	The base URL of your project, used for generating absolute URLs for your pages. `ECOPAGES_BASE_URL` overrides the default when `baseUrl` is omitted.
</ApiField>

<ApiField
	name="defaultMetadata"
	type="PageMetadataProps"
	defaultValue="{ title: 'Ecopages', description: 'This is a static site generated with Ecopages' }"
>
	Default metadata for your pages. This is merged with page-specific metadata when provided.
</ApiField>

<ApiField name="srcDir" type="string" defaultValue="src">
	The directory containing your source files, relative to the root project directory.
</ApiField>

<ApiField name="publicDir" type="string" defaultValue="public">
	The directory for static assets, relative to the src directory.
</ApiField>

<ApiField name="pagesDir" type="string" defaultValue="pages">
	The directory containing your page files, relative to the src directory.
</ApiField>

<ApiField name="includesDir" type="string" defaultValue="includes">
	The directory for include templates, relative to the src directory.
</ApiField>

Ecopages now discovers the document shell and error pages semantically:

- `src/includes/html.*` resolves the HTML template by basename and integration extension.
- `src/pages/404.*` resolves the not-found page by basename and integration extension.
- `src/pages/500.*` resolves the server-error page by basename and integration extension.

`eco.config.ts` has no field for these filenames. If no `pages/500.*` file or `app.serverError()` loader is configured, the page pipeline serves a built-in HTML 500 page. In development, custom and default 500 pages can show `message` and `stack` from the thrown error; the built-in page also includes a **Copy error** button.

<ApiField name="distDir" type="string" defaultValue="dist">
	The build output directory. Public files go into its `client/` subdirectory and private server output goes into `server/`. `ecopages start` does not read this option: it runs the only `<dir>/server/manifest.json` one level below the app root. Use `ecopages start --dist-dir <dir>` when there are several outputs (such as `dist-<scope>` per build target) or the output is nested (`out/web`) or a symlink.
</ApiField>

<ApiField name="workDir" type="string" defaultValue=".eco">
	The internal workspace used for development and runtime-only artifacts. This directory is not intended for
	deployment.
</ApiField>

<ApiField name="additionalWatchPaths" type="string[]" defaultValue="[]">
	Add additional files or directories to monitor during development. Paths are resolved from the project root, so
	`src/registry` watches every file inside that folder. An entry containing `*` is a glob pattern, such as
	`content/**/*.md` or `**/*.config.ts`; any other entry is a plain path, even with brackets. Globs are anchored at
	the project root: `*.css` matches only top-level files, and `**/*.css` matches at any depth. Ecopages watches the
	folder before the first wildcard (`content`, or the project root for a pattern starting with `**`) and reacts only
	to files that match. `*` and `**` do not match names starting with a dot unless the pattern spells the dot, as in
	`.github/**/*.yml`. To match a literal bracket in a glob, write `[[]`, as in `src/pages/[[]slug]/*.md`. A matching
	change invalidates server modules, notifies processors, and reloads the browser.
</ApiField>

<ApiField name="serverFiles" type="string[]">
	Globs, relative to the project root, of files copied into `dist/server/` at build so production code can read
	them next to `import.meta`. Two matches that share a basename fail the build. Prefer `public/` for static files
	the browser should fetch.
</ApiField>

<ApiField
	name="robotsTxt"
	type="{ preferences: RobotsPreference }"
	defaultValue={`{ preferences: { "*": [] } }`}
>
	Configuration for the robots.txt file.
</ApiField>

<ApiField
	name="sitemap"
	type="SitemapConfig"
	defaultValue="{ enabled: false, fileName: 'sitemap.xml', extraUrls: [], exclude: [] }"
>
	Automatic <code>sitemap.xml</code> generation during static export. Disabled by default. See{' '}
	<a href="/docs/core/sitemap">Sitemap</a> for eligibility rules, <code>exclude</code> patterns, and{' '}
	<code>extraUrls</code>.
</ApiField>

<ApiField name="integrations" type="IntegrationPlugin[]" defaultValue="[]">
	An array of integration plugins to enhance Ecopages functionality.
</ApiField>

<ApiField name="processors" type="Processor[]" defaultValue="[]">
	An array of processors to handle file transformations (e.g., Lightning CSS, Images).
</ApiField>

<ApiField name="loaders" type="EcoBuildPlugin[]" defaultValue="[]">
	An array of build plugins to use as loaders for custom file types. A plugin can also rewrite module source with its
	`transform` hook; there is no separate source-transform config option. See [Source Transforms](/docs/plugins/source-transforms).
</ApiField>

<ApiField name="cache" type="CacheConfig">
	Page cache settings: `store` (default `'memory'`), `defaultStrategy` for Pages that set none (default `'static'`),
	`enabled` (on in production builds, off in watch mode unless set), and `maxEntries` for the memory store (default
	`1000`). See [Caching](/docs/server/caching).
</ApiField>

<ApiField name="devPrewarmPaths" type="string[]" defaultValue="[]">
	Routes such as `/` or `/docs` to render in the background when the development server starts, so the first visit is
	fast.
</ApiField>

<ApiField name="devToolbar" type="DevToolbarConfig">
	Development-only in-browser inspector. Install `@ecopages/dev-toolbar` and set `devToolbar: devToolbar()`. See
	[Dev toolbar](/docs/core/dev-toolbar).
</ApiField>

## Request body size

<ApiField name="maxRequestBodySize" type="number" defaultValue="10485760">
	The most bytes of request body a route's `schema.body` reads before it answers HTTP 413 (10 MiB by default). It is
	checked against `Content-Length` first and counted while the body streams, so an oversized JSON, text, urlencoded or
	multipart body is refused without buffering more than the limit. A handler that reads `request` itself is not limited. Use
	`Infinity` for no limit. A value that is not above 0 fails when the config loads.
</ApiField>

```typescript
export default defineConfig({
	maxRequestBodySize: 2 * 1024 * 1024,
});
```

## Request URL and proxies

<ApiField name="trustProxy" type="boolean | { host?: boolean; proto?: boolean }" defaultValue="false">
	Whether `new URL(request.url)` takes its host and protocol from `X-Forwarded-Host` and `X-Forwarded-Proto`. By
	default the origin of `request.url` on the Ecopages server (Node or Bun) is the `Host` header the visitor sent, so `new URL(request.url).origin`
	is the address they used even behind a proxy that passes `Host` on; the address the server listens on is used only
	when `Host` is missing or is not a plain host. Set `trustProxy: true` only when every request comes through a proxy you
	control that overwrites both forwarded headers. When a proxy sets the protocol but passes the client's
	`X-Forwarded-Host` through, as some load balancers do, trust only that one: `trustProxy: { proto: true }` reads
	`X-Forwarded-Proto` and keeps `Host`; `{ host: true }` does the reverse. Any other client can send them, and an app that builds absolute links,
	redirects or compares `Origin` with the request origin would then trust a value the visitor chose. Only the first
	value of a comma separated forwarded header is read, and the protocol must be `http` or `https`.
</ApiField>

```typescript
export default defineConfig({
	trustProxy: true,
});
```

## Allowed hosts

<ApiField name="allowedHosts" type="string[] | true" defaultValue="the host of baseUrl in production; localhost and IP addresses in development">
	The hostnames the Ecopages server answers. A request whose host is not allowed gets HTTP 400 before routing, and a
	WebSocket upgrade for it is refused the same way. The host checked is the one `request.url` carries: the `Host`
	header, or `X-Forwarded-Host` when [`trustProxy`](#request-url-and-proxies) trusts it. Entries are hostnames, without
	scheme, port or path; `*.example.com` matches any subdomain of `example.com`, not `example.com` itself. `true` allows every host.
</ApiField>

This is the defence against DNS rebinding: an attacker's domain resolves to your server, so the browser sends the attacker's name as `Host` and `Origin`, and a check that compares the two would pass. Once a host is allowed, `request.url` is the address the visitor used, so any handler that compares `Origin` with it is sound.

- In development (`ecopages dev`), `localhost`, its subdomains and IP addresses are always allowed, together with the host of `baseUrl`. `allowedHosts` adds to them.
- In production (`ecopages start`, `node dist/server/app.mjs`), only the host of `baseUrl` (or `ECOPAGES_BASE_URL`) is allowed, so loopback and every other name are refused. `allowedHosts` replaces it: list the public host again, and `localhost` when a health check calls the server by that name.
- Ports are not compared. `app.fetch()` is not checked, since it takes the URL it is given, and `ecopages preview` serves only static files.

```typescript
export default defineConfig({
	baseUrl: 'https://shop.example.com',
	allowedHosts: ['shop.example.com', '*.shop.example.com', 'localhost'],
});
```

`allowedHosts: true` is unsafe: it turns the check off, so a rebinding attacker can reach the server by name. Use it only when a proxy in front of the server already refuses unknown hosts.

## Response headers

<ApiField name="headers" type="{ source: string; headers: Record<string, string> }[]">
	Headers added to every response Ecopages serves: rendered Pages, Explicit Routes and Endpoints, and files from `public/`
	and `dist/client`, under `ecopages dev`, `ecopages start` and `ecopages preview`. `source` is a URL pathname pattern
	that starts with `/`. `*` matches any characters except `/`, and `**` matches any characters including `/`; nothing
	else is a pattern. `/**` matches every path, `/assets/*` the files directly in `/assets/`, `/assets/**` everything
	below it, and `/**/*.wasm` every `.wasm` file. Rules apply in order. Framework headers such as `Content-Type`,
	`Cache-Control`, `ETag`, `Content-Encoding` and `Vary` stay, except that a configured header replaces one of the
	same name, so a rule can override one on purpose. An invalid `source` or header fails when the config loads.
	A static export carries no headers: set them on the host (see [Deployment](/docs/reference/deployment)), for example in a
	`_headers` file or the platform settings.
</ApiField>

```typescript
export default defineConfig({
	headers: [
		{ source: '/assets/*', headers: { 'Access-Control-Allow-Origin': '*' } },
	],
});
```

### WebAssembly and cross-origin isolation

`SharedArrayBuffer` and threaded WebAssembly need a cross-origin isolated page, which the browser grants from headers
on the HTML document itself:

```typescript
export default defineConfig({
	headers: [
		{
			source: '/**',
			headers: {
				'Cross-Origin-Opener-Policy': 'same-origin',
				'Cross-Origin-Embedder-Policy': 'require-corp',
			},
		},
	],
});
```

`self.crossOriginIsolated` is then `true`. Every cross-origin resource the page loads (images, scripts, fonts, iframes,
CDN files) must now send `Cross-Origin-Resource-Policy: cross-origin` or a matching CORS response, or the browser
blocks it. Same-origin files are unaffected. On a static export, send the same two headers from the host.

## Integrations

Ecopages supports various integrations to extend its capabilities. Here are some commonly used integrations:

- **Ecopages JSX**: Default stack for `.tsx` Pages and optional Radiant hydration
- **React**: React Pages or component islands
- **Lit**: Web Components
- **MDX**: Standalone Markdown on a non-React JSX runtime
- **KitaJS**: `.kita.tsx` Pages via `@kitajs/html`

To use an integration, install it and add it to your configuration. For example:

```typescript
import { defineConfig } from '@ecopages/core/config';
import { ecopagesJsxPlugin } from '@ecopages/ecopages-jsx';

export default defineConfig({
	baseUrl: 'https://example.com',
	integrations: [ecopagesJsxPlugin()],
});
```

For more details on specific integrations, refer to their respective documentation pages:

- [Ecopages JSX Integration](/docs/integrations/ecopages-jsx)
- [KitaJS Integration](/docs/integrations/kitajs)
- [Lit Integration](/docs/integrations/lit)
- [MDX Integration](/docs/integrations/mdx)
- [React Integration](/docs/integrations/react)
