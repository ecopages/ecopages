# React Integration

The `@ecopages/react` package introduces first-class integration with [React](https://reactjs.org/) version 19, enabling developers to build dynamic components using the latest React features within the Ecopages platform.

Also install React's required peer packages in your app: `react` and `react-dom`. In TypeScript projects, install `@types/react` and `@types/react-dom` as well.

## Usage

To enable React support, add the `reactPlugin` to your Ecopages configuration.

```typescript
import { defineConfig } from '@ecopages/core/config';
import { reactPlugin } from '@ecopages/react';

export default defineConfig({
	baseUrl: 'https://example.com',
	integrations: [reactPlugin()],
});
```

## Creating Components

### Standard (eco.component)

The standard way to create components in Ecopages is via the `eco.component` factory. This is ideal for managing dependencies (scripts, stylesheets) and enabling advanced features like lazy loading.

```tsx
import { useState } from 'react';
import { eco } from '@ecopages/core';

export const Counter = eco.component({
	dependencies: {
		stylesheets: ['./counter.css'],
	},
	render: () => {
		const [count, setCount] = useState(0);

		return (
			<div className="counter">
				<p>Count: {count}</p>
				<button onClick={() => setCount((prev) => prev - 1)}>-</button>
				<button onClick={() => setCount((prev) => prev + 1)}>+</button>
			</div>
		);
	},
});
```

### Plain React Components

You can also write standard React components directly when they only need React runtime behavior. A plain component can import its own stylesheet (`import './counter.css'`): Ecopages hands it to the nearest declared component, layout or page that imports the component.

Wrap a component in `eco.component()` only when it needs browser scripts, `modules`, stylesheet attributes, an `integration` override, or rendering by another Integration. A layout is a plain function typed with `LayoutProps` unless it needs one of those, then `eco.layout()`; the document shell uses `eco.html()`. A page of another Integration cannot render a plain React component; for a Kita or Ecopages JSX page the build fails and suggests `eco.component()`, which renders it as a Foreign Child.

```tsx
import { useState } from 'react';

export function SimpleCounter() {
	const [count, setCount] = useState(0);
	return (
		<button
			className="px-4 py-2 bg-blue-500 text-white rounded hover:bg-blue-600"
			onClick={() => setCount(count + 1)}
		>
			Count: {count}
		</button>
	);
}
```

### Using in Pages

Import the component and assign the layout on `eco.page()`. Ecopages discovers local component imports automatically.

```tsx
import { Counter } from '@/components/counter';
import { BaseLayout } from '@/layouts/base-layout';
import { eco } from '@ecopages/core';

export default eco.page({
	layout: BaseLayout,
	render: () => (
		<>
			<h1>Welcome to React on Ecopages</h1>
			<Counter />
		</>
	),
});
```

Hydratable React components stamp [island host attributes](/docs/core/island-hosts) on their SSR root for devtools and client hydration.

## Utilities

### `dynamic`

Use the `dynamic` utility to lazy-load components or render them only on the client.

```tsx
import { dynamic } from '@ecopages/react/utils/dynamic';

const HeavyComponent = dynamic(() => import('@/components/heavy-chart'), {
	ssr: false,
});
```

With `ssr: true`, `dynamic` returns a `React.lazy()` component, and the server renders its content into the HTML.

### Suspense on the server

Server rendering waits for every `<Suspense>` boundary before it returns HTML, in Pages, Layouts and every other React component they render, so `React.lazy()` and `<Suspense>` render their content, not their fallback. The document is still sent in one piece, not streamed. Waiting stops after 10 seconds by default. The limit covers the whole Page render, every React tree in it included: unfinished boundaries stay in their fallback for the browser to retry, the rest of the Page is served, and one warning names the Page. A tree that is still waiting outside every boundary has no HTML to serve, so the render fails instead. React components in a Page of another Integration each get the full limit. Pass `reactPlugin({ renderTimeoutMs: 5_000 })` to change the limit, a whole number of milliseconds from 1 to 2147483647. A component that throws, or an import that rejects, inside a boundary is logged on the server and that boundary's fallback is served for the browser to retry; an error outside every boundary fails the render. A boundary that renders a `<link rel="stylesheet" precedence>` also fails the render: declare the stylesheet as a Dependency instead.

### `ClientOnly`

The `ClientOnly` component is useful for parts of the UI that should strictly render in the browser (e.g., accessing `window` or `localStorage`).

```tsx
import { ClientOnly } from '@ecopages/react/utils/client-only';

<ClientOnly fallback={<Spinner />}>
	<BrowserSpecificFeature />
</ClientOnly>;
```

## Key Features

- **React 19**: Server rendering and hydration for standard React 19 components and hooks.
- **Fast Refresh**: Built-in Hot Module Replacement (HMR) for instant feedback.
- **MDX**: Built-in React MDX support through `reactPlugin({ mdx: {} })`.
- **Mixed Rendering**: React can own routes directly or resolve nested React boundaries inside non-React shells. Use [`EcoEmbed`](/docs/reference/eco-namespace#ecoembed) from `@ecopages/react/eco-embed` when a React page composes foreign-integration shells or passes children across integration boundaries.

## Mixed rendering and EcoEmbed

When a React route nests shells owned by another integration, import `EcoEmbed` from `@ecopages/react/eco-embed`. It wraps `eco.embed()` so the active foreign-child runtime can hand the subtree to the owning renderer.

```tsx
/** @jsxImportSource react */
import { eco } from '@ecopages/core';
import { EcoEmbed } from '@ecopages/react/eco-embed';
import { KitaShell } from '@/components/kita-shell';

export default eco.page({
	dependencies: {
		components: [KitaShell],
	},
	render: () => (
		<EcoEmbed component={KitaShell} props={{ id: 'kita-shell' }}>
			React-owned leaf
		</EcoEmbed>
	),
});
```

Plain opaque objects fail fast at core foreign-subtree queue boundaries; they are not coerced with `String(object)`. See [Ecopages JSX — Mixed Rendering](/docs/integrations/ecopages-jsx#cross-integration-children) for accepted child shapes and the queue contract.

## MDX Support

The React plugin includes optional MDX support. When configured, you can author `.mdx` pages alongside `.tsx` pages with unified client-side routing, hydration, and HMR.

```typescript
import { defineConfig } from '@ecopages/core/config';
import { reactPlugin } from '@ecopages/react';
import { ecoRouter } from '@ecopages/react-router';

export default defineConfig({
	baseUrl: 'https://example.com',
	integrations: [
		reactPlugin({
			router: ecoRouter(),
			mdx: {
				remarkPlugins: [],
				rehypePlugins: [],
			},
		}),
	],
});
```

This is the recommended approach when using a client-side router, as it ensures seamless navigation between TSX and MDX pages.

## Shared browser modules

With [`ecoRouter()`](/docs/ecosystem/react-router), Ecopages can keep outer Layout tiers mounted across client navigation (`persistLayouts` defaults to `true`). A package used by both a Layout and a Page must then be one browser module instance, or libraries with shared state, such as React context and TanStack Query, break.

Ecopages keeps every package to one instance without configuration. A production build bundles every browser entry of the app in one build with code splitting, so a package that several Pages, Layouts or islands import is one chunk with one URL. In `ecopages dev`, Page modules are served from `/assets/__eco_dev__/` and import each package from one vendor URL under `/assets/vendors/`; React, React DOM and the configured router are no exception. In production they are content-hashed chunks, cached `immutable`, and each page loads React once. Use the dev toolbar **Deps** panel to inspect the vendor URLs loaded by the active Page.

A library that depends on a singleton such as MobX or TanStack Query should declare it as a `peerDependency` and keep it external in its own build, so it imports the app's copy instead of inlining its own.

**Migration:** remove `runtimeModules` from `reactPlugin()`. The option no longer exists; packages it listed are shared automatically.

### Vendor troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Store updates / `reaction` / `observer` no-op | Duplicate singleton (for example MobX) — a library inlines one copy and app code loads another | Peer the singleton in the library and keep it external in the library build |
| `does not provide an export named …` in dev | An inline or non-module script imports a CommonJS package such as React by name, which the dev rewrite skips | Move the import into a module file or a non-inline `type="module"` script |
