# Asset Processing

**Layer:** Build.

This directory owns shared browser-build coordination and processed-asset pipelines.

Asset processing reads per-app state from the `AppRuntime` installed during config finalization. Each Integration owns an `AssetProcessingService` and its processed-asset cache. App-wide browser builds use the shared build queue, so static export can combine route assets before SSR requests.

## Purpose

Asset processing centralizes app-wide browser builds and processor-owned asset transformations.

Typical responsibilities include:

- asset factories, processors, and the processed-asset cache
- app-wide browser build coordination

## Main Areas

- `asset-processing-service/`: the only processed-asset cache, plus typed processors and asset factories. `getAssetDependencyKey` is the one dependency identity, shared by deduplication, the processed-asset cache and the production asset ledger (`AppRuntime.processedAssets`). It includes attributes, position, package role, `inline` and, for scripts, every `bundleOptions` field (each plugin as its name and `cacheKey`). File paths and bundled sources are relative to the app root. A generated script, a content script that lists `bundledSourceFilepaths` (a Page script bundle, a React Page or island entry, a lazy entry), hashes its text with those members, which it imports by absolute path, written relative to the app root, beside its name, and a package stylesheet (`fromPackage`) or a node-module script by its package path (`name@version/subpath`). No plugin `cacheKey` holds an absolute path, so every key survives moving the project or reinstalling its packages. `getDeclaredDependencyKey` leaves out `groupedBundle` and `bundle`, which the app-wide build and dependency preparation assign; the app-wide build keys its entries with it. Grouped results are reused only while their complete dependency sets match.
- `app-browser-client-build.ts`: combines static-export renderer plans, route islands, lazy client entries, the component scripts route preparation bundles, and HTML Page module scripts into one app-wide build; see the build README for the options that still separate entries. While a renderer plans its routes, it processes no component dependencies: the plan lists the scripts processing would bundle (`DependencyResolverService.collectBundleableScripts`) and every bundleable Page Browser Graph dependency, grouped or not, prepared once per route as its Integration prepares it. The build records each entry's output in the app runtime's `ProcessedAssetLedger` under the dependency key of every declaration that named it: a prepared script under its prepared key, an island or lazy entry under the key it was declared with. Preparation is a pure function of each dependency (`ensureGroupedContentScriptsBundle` and the ecopages-jsx hook return copies and name an entry from its own content), so any batch that prepares a script keys it the same. It also records every file it emitted, chunks included, and returns nothing route-shaped. Once a ledger holds that build, asset processing returns a recorded output for any script the build can bundle instead of bundling it on its own, the renderer resolves island and lazy entries the same way, and a script the build did not produce is bundled on its own as before. Each Integration's global scripts (`integrationDependencies`) join the same build as a plan without routes. `IntegrationPlugin.setup()` resolves none of them, and a production build activates Integrations with `deferGlobalScripts`; after the build, or after the Lit worker restores it, `resolveIntegrationDependencies()` fills the resolved list in place through `IntegrationPlugin.refreshResolvedIntegrationDependencies()`, so none is bundled on its own into `dist/`. `ecopages start` restores the ledger before any activation, and activation resolves them through it. Non-exact route templates and imported views receive a parameter-free plan without running route data hooks, and Dynamic Pages that declare `staticPaths` receive a plan per entry that runs `staticProps` so prop-dependent Dependencies are built. Any route instance whose dependencies the ledger records links them, planned or not. Static export still builds graphs while writing HTML.
- `browser-bundle.service.ts`: coordinates browser builds for assets and HMR. It records content-addressed outputs in `hashed-browser-asset.ts` for `immutable` file caching.

The asset-processing service owns the only processed-asset cache for its five processors, keyed by `getAssetDependencyKey`; file outputs retain their source path so development can verify freshness and invalidate imported inputs. Grouped and ungrouped processing share that cache, and a complete grouped result is reused only while its full dependency set matches. Integration-owned processing calls pass their Integration, whose optional `prepareAssetDependencies()` hook runs before dispatch; calls without an owning Integration pass `undefined`. The file-script processor reads the current HMR manager through the service getter rather than retaining a separately forwarded manager. A file script or stylesheet outside `srcDir` is emitted under `dist/client/assets`. A bundled script uses the bundler's `[name]-[hash]` name there, instead of a source-relative directory that would leave `dist`. An unbundled script or a stylesheet, including in development, uses the content hash from `writeHashedBrowserAsset`. With HMR on, a bundled script keeps the HMR output path. A development file inside `srcDir` keeps its source-relative path. The write of that path checks `isPathInside` before creating the file. A package stylesheet (`fromPackage`, from a discovered `import 'some-lib/style.css'`) skips Processors and the Page stylesheet bundle: `preparePackageStylesheet` tokenizes it, inlines its `@import`s (wrapped for their conditions, with remote ones and `@charset` hoisted), emits each file a relative `url()` or `image-set()` string names under a content hash in the same directory, refusing any outside the package, and rewrites the reference, so the ledger records it like any stylesheet and a sealed start serves it. In production the service also records every dependency it processes, content scripts and stylesheets included, in the app runtime's `ProcessedAssetLedger` (`processed-asset-ledger.ts`, keyed by `getAssetDependencyKey`, with app-root relative paths), the same ledger the app-wide build records its scripts in. `ecopages build` writes it to `dist/server/processed-assets.json`; `ecopages start` from a complete `dist/` restores and seals it. Once sealed, `processDependencies` is the one lookup gate: it returns every dependency's recorded output and runs no processor, writes no file and gzips nothing; a dependency the ledger does not record fails with "Run `ecopages build` again". A processor error, ungrouped or grouped, rejects `processDependencies`, so the build or request fails with the bundler's message; a Page is never written without a script it declared. A missing processor or a missing source file is still logged and skipped, and so is a processor error in a production server answering requests outside static generation (`staticGenerationActive`), because request-time rebuilds there can fail for reasons the build did not.

Grouped script assets share one processing path for file and content entries and use exact entry facade output lookup, so Page names such as `blog` and `blog-post` cannot select one another's hydration output. Static export combines compatible grouped entries from every Integration and the HTML shell scripts into app-wide browser build groups, then records each emitted entry in the ledger under the keys of the dependencies that declared it. The ordinary grouped cache reuses outputs only when the complete dependency-key set matches; entries from differently composed Page builds are never mixed. Grouped builds carry each entry's external modules, define values, and plugin instances; conflicting define values fail before bundling.
In development, each applied change batch is announced on the shared build-input index, and every asset-processing service evicts the cached assets whose source or bundled inputs it touched. Shared layout styles are therefore not rebuilt for every navigated page, and a bundle is never served after one of its imports changed.

Browser runtime module assets resolve bare package roots through their ESM import target. For legacy packages without an `exports` map, they prefer `package.json#module` over CJS `main`; CJS resolution is only a compatibility fallback. Generated entries use `export *` for ESM files and explicit named re-exports for CJS files (so bindings such as React `jsx` exist on the vendor). A default binding is added only when the selected entry exposes one. Runtime vendors are package-root contracts: subpath imports need their own vendor declaration or remain in the consuming bundle.

Package entry lookup is rooted at the application directory, so a framework-local dependency with the same name cannot shadow the application's installed package. ESM export conditions are evaluated in the same order as the generated vendor import (`node`, `import`, then `default`).

## Design Rule

Shared asset processing belongs here; framework-specific asset declarations stay with their Integration.
