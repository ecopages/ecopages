# Asset Processing

**Layer:** Build.

This directory owns shared browser-build coordination and processed-asset pipelines.

Asset processing reads per-app state from the `AppRuntime` installed during config finalization. Each Integration owns an `AssetProcessingService` and its processed-asset cache. App-wide browser builds use the shared build queue, so static export can combine route assets before SSR requests.

## Purpose

Asset processing centralizes app-wide browser builds and processor-owned asset transformations.

Typical responsibilities include:

- asset factories, processors, and the processed-asset cache
- app-wide browser build coordination and runtime asset declarations

## Main Areas

- `asset-processing-service/`: the only processed-asset cache, plus typed processors and asset factories. `getAssetDependencyKey` is the one dependency identity, shared by deduplication, the processed-asset cache, `AppRuntime.prebuiltBrowserScripts` and the manifest's component scripts. It includes attributes, position, package role, `inline` and, for scripts, every `bundleOptions` field (each plugin as its name and `cacheKey`). File paths, bundled sources and the members of a Page script bundle (which keys it instead of its text) are relative to the app root, so those keys survive moving the project; other generated content that embeds an absolute path still keys by location. React-generated entries are not portable yet: their generated content and plugin `cacheKey`s (client-graph boundary, `import.meta` preservation, alias resolver) capture absolute paths (#1028). `getIntegrationDependencyKey` scopes it to an Integration and leaves out `groupedBundle` and `bundle`, which the app-wide build and dependency preparation assign; build entries, route associations and the manifest's route entries use it. Grouped results are reused only while their complete dependency sets match.
- `app-browser-client-build.ts`: combines static-export renderer plans, route islands, lazy client entries, the component scripts route preparation bundles, and HTML Page module scripts into one app-wide build; see the build README for the options that still separate entries. While a renderer plans its routes, `DependencyResolverService` collects each bundleable component script instead of bundling it and hands out a placeholder asset. After the build, the outputs are recorded by dependency key in `AppRuntime.prebuiltBrowserScripts`, every placeholder is filled in place, and asset processing returns a recorded output instead of bundling that script on its own. A script the build did not produce is bundled on its own as before. Each Integration's global scripts (`integrationDependencies`), except browser runtime assets with fixed URLs, join the same build as a plan without routes; after the build, or after `ecopages start` restores it, `IntegrationPlugin.refreshResolvedIntegrationDependencies()` replaces the resolved list in place. `app-browser-client-manifest.ts` persists route associations and the component script outputs under their dependency keys, which need no rewriting after the project moves, so `ecopages start` and the Lit static-render worker can restore outputs before rendering. Non-exact route templates receive a parameter-free plan without running route data hooks, and Dynamic Pages that declare `staticPaths` receive a plan per entry that runs `staticProps` so prop-dependent Dependencies are built. Later params reuse a planned graph when dependencies match. After `ecopages start` restores the manifest, a request whose graph is not listed is an error; it is never built. Static export still builds graphs while writing HTML.
- `browser-bundle.service.ts`: coordinates browser builds for assets and HMR. It records content-addressed outputs in `hashed-browser-asset.ts` for `immutable` file caching.

The asset-processing service owns the only processed-asset cache for its five processors, keyed by `getAssetDependencyKey`; file outputs retain their source path so development can verify freshness and invalidate imported inputs. Grouped and ungrouped processing share that cache, and a complete grouped result is reused only while its full dependency set matches. Integration-owned processing calls pass their Integration, whose optional `prepareAssetDependencies()` hook runs before dispatch; calls without an owning Integration pass `undefined`. The file-script processor reads the current HMR manager through the service getter rather than retaining a separately forwarded manager. A file script or stylesheet outside `srcDir` is emitted under `dist/client/assets`. A bundled script uses the bundler's `[name]-[hash]` name there, instead of a source-relative directory that would leave `dist`. An unbundled script or a stylesheet, including in development, uses the content hash from `writeHashedBrowserAsset`. With HMR on, a bundled script keeps the HMR output path. A development file inside `srcDir` keeps its source-relative path. The write of that path checks `isPathInside` before creating the file.

Grouped script assets share one processing path for file and content entries and use exact entry facade output lookup, so Page names such as `blog` and `blog-post` cannot select one another's hydration output. Static export combines compatible grouped entries from every Integration and the HTML shell scripts into app-wide browser build groups, then attaches each emitted entry to its routes. The ordinary grouped cache reuses outputs only when the complete dependency-key set matches; entries from differently composed Page builds are never mixed. Grouped builds carry each entry's external modules, define values, and plugin instances; conflicting define values fail before bundling.
In development, each applied change batch is announced on the shared build-input index, and every asset-processing service evicts the cached assets whose source or bundled inputs it touched. Shared layout styles are therefore not rebuilt for every navigated page, and a bundle is never served after one of its imports changed.

Browser runtime module assets resolve bare package roots through their ESM import target. For legacy packages without an `exports` map, they prefer `package.json#module` over CJS `main`; CJS resolution is only a compatibility fallback. Generated entries use `export *` for ESM files and explicit named re-exports for CJS files (so bindings such as React `jsx` exist on the vendor). A default binding is added only when the selected entry exposes one. Runtime vendors are package-root contracts: subpath imports need their own vendor declaration or remain in the consuming bundle.

Package entry lookup is rooted at the application directory, so a framework-local dependency with the same name cannot shadow the application's installed package. ESM export conditions are evaluated in the same order as the generated vendor import (`node`, `import`, then `default`).

## Design Rule

Shared asset processing belongs here; framework-specific asset declarations stay with their Integration.
