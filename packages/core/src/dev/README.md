**Layer:** Development and HMR.

Development-only browser tooling is opt-in per application.

## Development invalidation

The [invalidation service](invalidation/README.md) classifies file changes and marks affected development results dirty. Each `AppRuntime` owns one instance shared by the Project Watcher and HMR manager.

## Dev toolbar

- `/_dev_toolbar.js` — browser bundle built by core from `devToolbar.package` (for example `@ecopages/dev-toolbar`)
- `#__ECO_DEV_MANIFEST__` — per-page dependency graph payload for the Deps panel
- Build errors — the reference toolbar claims HMR error presentation; custom clients use the [build error event contract](../dev-toolbar/README.md#build-error-presentation), with an in-page fallback for unclaimed errors

Public docs: [Dev toolbar](/docs/core/dev-toolbar) (built-in apps, manifest fields).

Configure in `eco.config.ts`:

```ts
import { defineConfig } from '@ecopages/core/config';
import { devToolbar } from '@ecopages/dev-toolbar/config';

export default defineConfig({ devToolbar: devToolbar() });
```

For a custom client package, use `defineDevTool` from `@ecopages/core/client`.

Install the client package in the app project. Core resolves it from the application root and bundles it during watch mode.

Disable per project with `devToolbar: { enabled: false }`, or per process with `ECOPAGES_DEV_TOOLBAR=false` or `0`.

Server wiring: [dev-toolbar/README.md](../dev-toolbar/README.md) (manifest and the toolbar runtime entry that the HMR manager bundles, serves and injects). Bring-your-own toolbars export `src/bootstrap.ts` and use the same `devToolbar.package` config key.

### Dev transform

Entrypoints may be files under `srcDir` or files in workspace-linked packages. Workspace files are served at `/assets/__eco_dev__/@fs/...` so a React island from a linked package can hydrate on another Integration's page. Module URLs encode filesystem characters such as spaces, percent signs, and query or fragment delimiters and decode them before resolving the source path.

A relative module Worker URL (`new Worker(new URL('./x.ts', import.meta.url), { type: 'module' })`, or `SharedWorker`) in a served module points at the worker's own versioned dev transform URL, and the worker is served like any other module; the build skips its own worker entries for these one-module builds. A classic worker fails the module with the same error as a production build, so does a relative URL that does not resolve or has a query, and any other Worker URL, such as a `new URL()` held in a variable, is left as written with a warning naming the file.

Dev transform requests retry when their source changes or is invalidated during compilation. Concurrent requests share one in-flight compile per source, including across source and global invalidation; stale attempts release their slot before retrying. Only results for the current source snapshot enter the module cache, so rapid edits cannot label stale browser code with a newer source hash. A failed compile of a snapshot that changed in the meantime is retried the same way, so it is neither returned nor reported.

### Build errors of served modules

When a module fails to compile, `DevTransformServer` answers 500 with the error text, records the message under the module, and calls `onTransformError` with it. `HmrManager` broadcasts that message as an HMR `error` event, which the HMR client shows in the page ([hmr/README.md](../hmr/README.md#client-events)).

- The failure is recorded under the requested module, but its cause can be another file and the module can be removed, so `HmrManager.handleFileChanges()` clears every recorded failure. A module that still fails records its error again on its next request. A successful request also removes its module's failure.
- The module request of a fresh page load can arrive before the page's HMR socket connects, and the broadcast then reaches no one. The Node HTTP host therefore calls `sendPendingBuildErrors()` right after subscribing a socket, which sends one `error` event per recorded failure.
- A changed file whose HMR strategy or script-change handler throws sends its error once, with the rest of its batch, and only when the batch is broadcast. `HmrManager` records it under that file until the file processes without error, and `sendPendingBuildErrors()` sends it too, so the error survives a `reload` from another file of the same save.

Bare browser imports are prebundled into one vendor graph, the way Vite pre-bundles dependencies. Every known dependency entry (each resolved package entry that an app module imports by a bare specifier) is an entry of one code-split Rolldown build, served at `/assets/vendors/<name>.<entry-hash>.js`. A module that two entries reach, such as a file shared by a package root and its subpath, a package that several packages import, or a CommonJS module that several packages `require()`, lands in one shared chunk (`/assets/vendors/<chunk>-<content-hash>.js`) that the entries import relatively, so it loads once and keeps one module identity. `@ecopages/core` resolves with browser-first conditions and other packages module-first, and since a build takes one condition list, each list has its own graph. A module-first package's `@ecopages/core` imports are not bundled into its graph: they become external imports of core's browser-first entry URLs, so core loads once.

React, React DOM, the React bootstraps and the React router are ordinary entries of the module-first graph; no Integration rewrites their imports. A CommonJS entry such as `react` is served with `module.exports` as its default export and no named exports. The build reports which entries are CommonJS (`dependencyGraph.commonJsEntrypoints`, from Rolldown's `inputFormat`), and the import rewriter turns an import of one into a default import plus property reads, with the interop the production build applies (Rolldown's `__toESM` outside Node mode): named imports read `module.exports`, and `default` is `module.exports.default` when the module sets `__esModule`, otherwise `module.exports`. `import()` resolves to the same namespace; `export *` of such a vendor re-exports nothing and logs a warning. No export names are read from packages at build time. While HMR is on, the content-script processor runs the same rewrite on unbundled module content scripts, through `IHmrManager.rewriteModuleImports`, so generated bootstraps import packages by name. Browser builds define `process.env.NODE_ENV` like `import.meta.env.NODE_ENV`, so React's CommonJS entry picks its development build here and its production build in the app-wide build.

A later build must not change a file an earlier one served, or the page reloads. A dev-transform contributor can declare the bare specifiers its generated modules import (`getVendorEntries`), which join the graph before its first build. It returns `{ resolveFrom, specifiers }` (`DevTransformVendorEntries`): `resolveFrom` is a directory inside the contributing package, such as `import.meta.dirname` of the contributor's module, and the specifiers resolve from it, so a dependency only that package declares joins the first build without the app declaring it. React declares its packages, bootstraps and router, resolved from `@ecopages/react`. Each build also has a pin entry that re-exports every Rolldown runtime helper and the namespace of every entry with no `import` or `export` statement, so the shared runtime chunk and each CommonJS entry's `require` export are the same in every build instead of growing as packages arrive.

`DevTransformVendorRegistry` resolves a new bare specifier from the directory of the module that imports it, as Node and the production build do, so a dependency that only an integration package declares resolves under a strict pnpm install. Entries are keyed by the resolved file: importers that reach the same file share one entry, and two installed versions of a package are two entries with two URLs. When a package resolves to more than one installed copy, the registry logs a warning naming each copy's directory and the directories of its importers, once per set of copies, so an accidental second React is visible. Inside a vendor entry, Rolldown resolves the entry's own imports from the entry's real path. A dev-transform contributor's declared specifiers resolve from the directory it names inside its own package (`DevTransformVendorEntries.resolveFrom`). Each entry keeps every specifier and directory pair that reached it. The registry adds the entry, and rebuilds that graph after a 50 ms quiet period, which collects the bare imports of one page load into one build; the import rewriter resolves every specifier of a module at once, so its new bare imports share that build, and gets each entry URL once the build finishes, or its prebundle error. Entry URLs depend only on the specifier and the entry path, so they stay the same across rebuilds. When a rebuild changes or drops a vendor file that a browser already received from it or from an earlier build it kept unchanged, the registry calls `onVendorGraphChange` and `HmrManager` broadcasts `reload`, since a page that kept the old chunks could otherwise load a second copy of a module. A failing graph build is retried entry by entry: when some entries fail alone and others build, the failing entries keep their error (a `500` with the prebundle error, and a rejected URL resolution) until the next invalidation, and the graph builds again without them. When no single entry is isolated, or anything throws, including the vendor plugin resolver, the graph failed as a whole: the error is logged, every entry keeps serving the output of the last good build, an entry with no such output answers with the error, and no entry is marked failed, so the next build tries them all again; a request for an entry that has no output, made 2 s or more after the failure, schedules that build, so the error does not stick and a lasting failure does not rebuild on every request. `DevTransformServer` stats the lockfiles and install manifests (such as `node_modules/.modules.yaml`) of the app and of the nearest ancestor with a lockfile on asset requests, at most once per 300 ms; when one changes it invalidates every compiled module and vendor graph, clearing the bare package resolvers' filesystem caches and resolving each known specifier again from every directory that reached it, so each importer moves to the file it now reaches, a source whose directory no longer exists is dropped, and a package install during the session takes effect without a restart. Until the rebuild commits, entry URLs wait for it while chunk URLs are still served from the previous build, so an open page can load its lazy chunks. After each build every known specifier and directory pair, failing ones included, is written to `dev-vendor-entries.json` in the work directory, and the next dev process seeds its graphs from that file, skipping specifiers that no longer resolve from their directory and ignoring a file written without directories, so it builds the full graph on its first request instead of rebuilding and reloading. The bundle contents stay in that process's memory; Core does not write them under `dist` or reuse them from disk. A process restart rebuilds them from the installed package graph, so a change to a transitive dependency takes effect even when the importing package's version and entry file stay the same. Every vendor file is served with `Cache-Control: no-cache` and a content `ETag`; browsers revalidate on each load and receive `304` while the content is unchanged.

## Additional watch paths

The Project Watcher resolves each `additionalWatchPaths` entry against the root directory. A plain path is watched as given and matches itself and everything inside it. An entry containing `*` is a glob, so the pattern is split at its first segment with a glob character. The static prefix, resolved against the root directory, is the base the watcher subscribes to (`content` for `content/**/*.md`, the root directory for `**/*.config.ts`), and the rest is matched with `path.matchesGlob` against paths relative to that base, so glob characters in the root directory path never reach the matcher. A path segment starting with `.` matches only a pattern segment starting with `.`. The watcher ignores files and dot-directories reached only through a glob base unless the glob can match them, and warns when a glob's base is the filesystem root. On Windows a pattern may separate segments with `\\` or `/`.

The watcher filters `node_modules`, `.git`, the work directory and `distDir` from indexing and reported changes. Native recursive watchers may still observe events below a watched root before the filter runs. Paths are checked with the platform's native path rules, including on Windows.

The Project Watcher waits up to 30 seconds for its filesystem subscription to become ready. A timeout or an error before readiness closes the subscription and rejects watcher startup. Its maximum-wait timer schedules sustained change batches within one second of the first event; serialized processing can begin later when earlier work is queued.

## Process restarts

The Project Watcher classifies the resolved `eco.config` module, the project files it imports (`absolutePaths.configModuleFiles`), and supported project dotenv paths separately from HMR. Under the CLI, those changes request a graceful runtime stop and a supervised child-process restart so config modules and environment values are loaded from scratch. When the restarted child exits with an error, the CLI supervisor waits for the next change in the project or a linked workspace package and launches again instead of exiting. It watches from before the restarted child launches, skipping dependencies, VCS metadata and the default work and build directories (`resolveDevelopmentRecoveryWatch`), so a fix saved while the child was loading relaunches at once. A Project Watcher with no restart callback warns and returns. Runtime entry watchers own changes to `eco.config.ts` itself when `dev:watch` is active; the Project Watcher still owns dotenv files and files the config imports. Watcher errors retain their stacks in the log.

During `ecopages dev`, the Project Watcher resolves linked package roots from the application's declared dependencies and activates a root when a recorded build input lies inside it. Adding, editing, or deleting a file in an active root requests a supervised restart, reloading server imports and rebuilding browser vendors. Their `node_modules` and dot entries are skipped. Vendor bundles live only in the running process, so the restarted process builds them from the current package files. See [Project Watcher](../watchers/README.md) for discovery and restart behavior.
