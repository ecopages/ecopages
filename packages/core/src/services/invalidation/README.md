# Development Invalidation

File-change classification and the batch entry that marks development results dirty.

`DevelopmentInvalidationService.planFileChange()` classifies one path. Config, files the config imports, and dotenv files are `runtime-restart`. Route files are `route-source`; other server files and recorded build inputs are `source`. Browser builds return their plugin inputs and module closures on `BuildResult`, and route-module closures are bound to their source route. HTML entries register the route closure, browser graph, processed asset, and render-shell inputs they used, and the render shell includes the HTML template's imports. Any edit evicts only the entries that recorded the file. An `additionalWatchPaths` match clears every cached HTML document, because the framework cannot infer which pages read an arbitrary watched file. The Page Browser Graph and HMR entrypoint reverse lookups use the same index. The Project Watcher owns the trailing debounce (150 ms by default) and schedules sustained batches no later than one second after their first event; serialized processing can begin later if earlier work is queued. For a batch without a restart input, `applyDevFileChanges({ changed, created, deleted })` plans the received paths once and marks those results dirty. Rebuild happens on the next request that needs a result.

`created` stays separate because new Page files refresh the Route Registry. For a non-restart batch, the Project Watcher calls `applyDevFileChanges` once and runs its batch-level browser update handling once. Matching Processors receive one `onChanges` callback for the batch. Restart batches return through the runtime lifecycle without applying invalidation, Processor notification, or browser update handling.
