# Project Watcher

The Project Watcher recursively watches `srcDir` and any configured pages, components, includes, layouts or public directory that resolves outside it, plus recorded build inputs outside it, restart files, workspace-linked package roots, and configured additional watch paths. Recorded inputs include plugin `addDependency` paths, module closures, and Processor watch roots; they select which builds and caches a change invalidates without narrowing source-directory coverage. Startup waits up to 30 seconds for Chokidar’s `ready` event before the server advertises readiness, so the first edit cannot race initial filesystem subscription. A startup error or timeout closes the watcher and rejects initialization. `ignoreInitial` prevents existing files from being treated as new at startup. Subscription replays paths already recorded during initialization or Page rendering and adds paths recorded after listen. Chokidar emits no `add` for an existing path passed to `watcher.add`, so subscribing a recorded input after listen is not treated as a create. Genuine new source files invalidate immediately, including files copied with preserved timestamps. Linked-package creates still request a restart.

Filesystem events use a trailing debounce with a 150 ms default; setting `changeDebounceMs` to `0` disables debouncing. With debouncing enabled, the maximum-wait timer schedules the batch no later than one second after its first event. Processing remains serialized behind earlier work, so it can start later. Closing the watcher drops scheduled batches that have not started. For a batch without a restart input, the watcher calls `applyDevFileChanges({ changed, created, deleted })` once. That marks server modules, Page Browser Graph records, HTML cache entries, and route-module records dirty without rebuilding them. An unopened Page is rebuilt on the next request. Each Processor that watches matching extensions receives one `onChanges({ created, changed, deleted, bridge })` callback for the batch, and the watcher runs its batch-level browser update handling once; creating and deleting Pages in the same window refreshes the Route Registry once. Dotenv and linked-package batches, and config-module batches not owned by a runtime entry watcher, return through the runtime restart lifecycle.

At startup it resolves the application's declared dependencies, development dependencies, and optional dependencies through installed package directories, including hoisted installs. Real package roots outside any `node_modules` segment are watched directly. This covers server-only imports and packages with subpath-only exports without waiting for a browser request. Missing optional packages are skipped; aliases to the same root share a subscription.

Adding, changing, or removing a linked package file requests a runtime restart before HMR or Processor notifications. The existing lifecycle coalesces pending restart requests and delegates shutdown to the process that owns the watcher. Before a workspace restart, generated `dist/assets/vendors` output is discarded: an unchanged package may contain bundled code from another edited linked dependency. The next process reloads server imports and rebuilds browser vendors. A watcher with no restart callback warns and returns.

Linked package `node_modules` and dot entries are ignored. Application work and dist directories remain ignored, while application dotenv files remain restart inputs. Discovery runs again on startup; changing the application's dependency declarations or links requires restarting the session. Dependencies declared only by another package are not discovered transitively.
