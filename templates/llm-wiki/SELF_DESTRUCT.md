# Bootstrap this wiki

You are reading this because someone just scaffolded a fresh `llm-wiki` (via `npx ecopages init <dir> --template llm-wiki`) and handed you this file to set it up. This is a one-time onboarding script, not a permanent part of the wiki: see the last section for why it deletes itself.

Work through the steps in order. Don't skip ahead to generating content before the user has agreed the schema fits.

## 1. Orient

Read [`SCHEMA.md`](./SCHEMA.md) and [`AGENTS.md`](./AGENTS.md) in full. They define the wiki's structure: `sources/` (immutable inputs), `wiki/` (the pages you'll maintain, organized into `app` / `package` / `concept` / `recipe` / `entity` / `decision` categories), `index.md` and `log.md` (both generated/append-only).

The `wiki/` and `sources/` directories right now hold demo content: pages documenting the llm-wiki template itself (`wiki/app/demo.md`, `wiki/concept/wiki-structure.md`, `wiki/recipe/maintain-wiki.md`, and a few more, plus `sources/source-demo.md`). That's expected: it's there to show the pattern, not to be kept. You'll clear it in step 4.

Then ask the user what this wiki is for: a codebase, a product, a research area, personal notes, something else. You need this before the schema discussion means anything.

## 2. Discuss the schema: don't assume it fits

The six default categories were designed with a software repo in mind. They may not fit what this user is documenting. Walk through them with the user and ask, concretely:

- Do these six categories cover their content, or are some irrelevant / is something important missing?
- Does the concept-vs-recipe split ("why / what must stay true" vs "how to do it here, with a pointer to a reference implementation") make sense for their material, or is that distinction meaningless for them?
- Does `paths` (required on recipe pages, pointing at a reference implementation file) make sense, or does their content have no equivalent of "a file in a repo"?

If they want changes, edit `SCHEMA.md` together before moving on: category names, the frontmatter fields, whatever needs to flex. A renamed or removed category isn't just a prose edit: rename or delete the matching `wiki/<category>/` directory, update that directory's `sortspec.md`, and update the category list in the root `wiki/sortspec.md` to match, so the schema and the directory layout never drift apart. Don't generate wiki pages against a schema the user hasn't actually endorsed; that just means redoing the work later.

## 3. Confirm before generating anything

Once the schema looks right, stop and ask explicitly: **"Ready to initialize the wiki now?"** Wait for a clear yes. Don't start ingesting sources or writing pages on your own read of the conversation: the user needs to have actually said go.

## 4. Initialize

First, clear the demo content so it doesn't sit alongside the user's real pages: delete the demo pages under `wiki/` (and any now-empty category directories, along with their `sortspec.md`), and delete `sources/source-demo.md`. Confirm with the user before deleting anything you're unsure is demo content versus something they already edited. Leave `index.md` and `log.md` alone for now: don't hand-edit `index.md`, it's a generated file (see below).

Then follow the **Ingest** operation in `SCHEMA.md`: ask the user what to ingest first (existing docs, a codebase, notes: whatever they pointed you at in step 1), read it, discuss key takeaways with them, save raw inputs under `sources/`, write the first `wiki/` pages (with `summary` frontmatter), and append a `log.md` entry.

`index.md` is generated by the app's ingest pipeline, not written by hand: if you can run shell commands, run `pnpm --filter @ecopages/template-llm-wiki build` (or `cd app && pnpm build`) to regenerate it from the current `wiki/` contents, then run `pnpm --filter @ecopages/template-llm-wiki lint:wiki` to catch broken links, orphan pages, or sortspec mismatches before calling this pass done. If you can't run shell commands, tell the user to run both from the project root once you're finished editing `wiki/`.

Keep this to a first useful pass, not an exhaustive one. The wiki grows through ongoing ingest and query afterward: this step just needs to leave the user with a working, correctly-shaped starting point.

## 5. Self-destruct

Once the user confirms the initial pass looks right, delete this file: run `rm SELF_DESTRUCT.md` (or your file-deletion tool's equivalent) from the wiki root. Also remove the `predev` line from `app/package.json`: it only exists to print a reminder pointing at this file when someone runs `pnpm dev` before it's been read, and that reminder has nothing left to say once you're here. Then tell the user you've done both.

This file only makes sense once, on a fresh scaffold: if it stuck around, a later agent picking up this wiki could mistake it for a live instruction and re-run onboarding on a wiki that's already in use. Do not delete it before step 3's confirmation: if the setup conversation gets cut off partway through, the next agent still needs it to pick up where you left off. If you don't have file-deletion access, tell the user to remove it themselves and give them the exact command.
